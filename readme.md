# Meeting Proxy

Meeting Proxy is a small local application that checks whether meeting notes
were addressed by a meeting transcript. The current tiny UI lets a user click
one button and view the status, supporting evidence, and confidence for every
note.

The project also contains separate Pocket TTS voice-recording and voice-cloning
examples. Those examples are not part of the meeting-analysis request flow.

## What the Tiny UI Does

The React UI calls `POST http://127.0.0.1:8000/analyze` when the user clicks
**Analyze Meeting**. The backend then:

1. Reads meeting notes from `backend/data/notes.md`.
2. Reads the transcript from `backend/data/transcript.txt`.
3. Splits the transcript into overlapping three-line windows.
4. Embeds the windows with Sentence Transformers using
     `all-MiniLM-L6-v2`.
5. Stores those embeddings in an in-memory ChromaDB collection.
6. Retrieves the three most relevant transcript windows for each note.
7. Sends each note and its retrieved evidence to Ollama using
     `llama3.2:3b`.
8. Validates Ollama's response with Pydantic.
9. Returns the results to React, which renders one card per note.

The system does not currently accept transcript uploads. It always reads the
two files under `backend/data/`, and paths are resolved relative to the
directory from which Uvicorn is started.

## Result Format

`POST /analyze` returns an object with a `notes` array:

```json
{
    "notes": [
        {
            "id": 0,
            "text": "Decide on the database for the new backedn",
            "status": "completed",
            "evidence": "The participants agreed to use PostgreSQL.",
            "confidence": 0.95
        }
    ]
}
```

`status` is one of `completed`, `partial`, or `open`. `confidence` is a
number from `0.0` to `1.0`. The API currently returns the evidence text
generated by Ollama, not the raw retrieved transcript windows.

## Prerequisites

- Windows PowerShell
- Python 3.14 or another version supported by the installed wheels
- Node.js and npm
- Ollama
- An NVIDIA GPU and compatible CUDA setup are recommended for the pinned CUDA
    Torch installation, but the embedding and TTS code can use CPU where
    supported

The repository includes a ready-made virtual environment in `meet_proxy/`.
Use its interpreter directly if activation is inconvenient.

Install or verify the Python packages in the virtual environment. If a
dependency lock file is available in your checkout, install it with the
PyTorch CUDA index:

```powershell
.\meet_proxy\Scripts\Activate.ps1
python -m pip install -r .\requirements-freeze.txt `
    --extra-index-url https://download.pytorch.org/whl/cu126
```

The extra index is needed for a requirement such as
`torch==2.14.0+cu126`; that CUDA build is not resolved from the normal PyPI
index alone. If the lock file is absent, install the backend packages used by
the current source (`fastapi`, `uvicorn`, `chromadb`, `sentence-transformers`,
`ollama`, and `pydantic`) plus the packages required by the voice examples
(`pocket-tts`, `sounddevice`, `numpy`, `scipy`, and `torch`).

Install and prepare Ollama:

```powershell
ollama pull llama3.2:3b
ollama list
```

The model name must match `MODEL_NAME` in `backend/app/llm.py` unless that
constant and this README are changed together.

## Run the Meeting Analyzer

Open two PowerShell terminals from the repository root.

### Terminal 1: Backend

Start Uvicorn from `backend/`. This working directory matters because
`main.py` reads `data/notes.md` and `data/transcript.txt` using relative paths.

```powershell
.\meet_proxy\Scripts\Activate.ps1
cd .\backend
python -m uvicorn app.main:app --reload
```

The API is available at `http://127.0.0.1:8000`. Useful checks are:

```powershell
Invoke-WebRequest http://127.0.0.1:8000/
Invoke-WebRequest http://127.0.0.1:8000/analyze -Method Post
```

The first analysis can take longer because Sentence Transformers may download
`all-MiniLM-L6-v2` and Ollama may load `llama3.2:3b` into memory.

### Terminal 2: Frontend

```powershell
cd .\frontend
npm install
npm run dev
```

Open the URL printed by Vite, usually `http://localhost:5173`. The frontend
expects the backend at `http://127.0.0.1:8000` and the backend CORS settings
currently allow `http://localhost:5173`.

Production-style frontend checks are available with:

```powershell
npm run lint
npm run build
npm run preview
```

## Backend File Details

### `backend/app/main.py`

Creates the FastAPI application and a module-level `TranscriptRetriever`.

- `app = FastAPI(title="Meeting Proxy")`: application object imported by
    Uvicorn as `app.main:app`.
- CORS middleware: permits the Vite origin `http://localhost:5173`, all HTTP
    methods, credentials, and headers.
- `GET /`: `root()` takes no arguments and returns
    `{"message": "Meeting Proxy API"}`.
- `POST /analyze`: `analyze_meeting()` takes no request body or parameters.
    It returns `{"notes": results}` after processing every note.

For each note, `analyze_meeting()` calls `retriever.search(note, top_k=3)`.
That returns evidence dictionaries, then calls
`classify_note(note, evidence)`. The validated `NoteAnalysis` fields are
converted to JSON-compatible values before being added to the response.

### `backend/app/matcher.py`

Contains file-loading helpers:

- `load_notes(path: str) -> list[str]`: receives a filesystem path, reads
    UTF-8 text, and returns every line matching `- note text` as a list of note
    strings.
- `load_transcript(path: str) -> str`: receives a filesystem path, reads
    UTF-8 text, and returns the complete transcript string.

These functions do not validate that the path exists; a missing file raises a
normal Python file error and causes the request to fail.

### `backend/app/retriever.py`

Defines `TranscriptRetriever`, which owns the embedding model and ChromaDB
collection.

- `__init__()`: takes no arguments. Loads `all-MiniLM-L6-v2`, creates a local
    ChromaDB client, and gets the `meeting_transcript` collection.
- `chunk_transcript(transcript: str, window_size: int = 3) -> list[str]`:
    receives the full transcript and window size. It removes blank lines and
    returns overlapping newline-joined windows. A short transcript is returned
    as one chunk; an empty transcript returns `[]`.
- `clear_collection()`: takes no arguments and deletes/recreates the current
    Chroma collection.
- `index_transcript(transcript: str)`: clears old data, chunks the transcript,
    computes embeddings, and upserts documents with IDs such as `chunk_0`.
    It returns `None`.
- `search(note: str, top_k: int = 3) -> list[dict]`: receives a note and the
    maximum number of results. It returns dictionaries with `text` and
    `distance` keys, for example
    `{"text": "Alice: ...", "distance": 0.24}`. Blank notes or an empty
    collection return `[]`.

The Chroma client is in memory. The transcript is cleared and reindexed for
every `/analyze` request, so this is not yet a persistent vector database.

### `backend/app/llm.py`

Defines the Ollama classification call:

- `MODEL_NAME`: currently `llama3.2:3b`.
- `classify_note(note: str, evidence: list[str]) -> NoteAnalysis`: receives
    one meeting note and the retrieved evidence dictionaries. It builds a prompt
    containing the evidence text, calls Ollama's `chat()` with JSON schema
    formatting, parses the returned content, and validates it as `NoteAnalysis`.

The function returns `NoteAnalysis`, not a plain dictionary. Invalid JSON,
missing fields, invalid status values, or confidence values outside `0.0` to
`1.0` raise `ValueError` after printing the raw model response for debugging.

### `backend/app/models.py`

Defines the data contracts used by the backend:

- `NoteStatus`: string enum with `OPEN`, `PARTIAL`, and `COMPLETED` values.
- `NoteAnalysis`: requires `status: NoteStatus`, `evidence: str`, and
    `confidence: float` constrained to `0.0 <= confidence <= 1.0`.
- `Note`: represents an API result with `id`, `text`, status, optional
    evidence, and optional confidence.
- `MeetingAnalysis`: wraps a list of `Note` objects. The current endpoint
    returns an equivalent dictionary directly rather than declaring this model
    as its response model.

## Frontend File Details

### `frontend/src/App.jsx`

`App()` owns three pieces of React state:

- `results`: the note result array returned by the API.
- `loading`: disables the button while the request is running.
- `error`: stores a user-visible request error string.

`analyzeMeeting()` sends a `POST` request with no body to the backend URL,
checks `response.ok`, parses `response.json()`, and stores `data.notes` in
`results`. The component then maps each result to a card showing `text`,
`status`, `evidence`, and `confidence` as a percentage.

### `frontend/src/main.jsx`

Imports the global stylesheet and `App`, finds the HTML element with ID
`root`, and mounts `<App />` inside React `StrictMode`. It sends no data to
the backend itself.

### `frontend/src/App.css`

Contains the UI-specific styles for the header, analyze button, error panel,
result section, note cards, and status colors. It does not make network calls.

### `frontend/src/index.css`

Contains global/template styles, CSS variables, typography, page sizing, and
light/dark color-scheme rules. `App.css` overrides these where needed for the
meeting UI.

### `frontend/index.html`

Defines the browser document, the `root` mount element, and the module script
that loads `/src/main.jsx`.

### `frontend/package.json`

Defines the npm scripts:

- `npm run dev`: start Vite development server.
- `npm run build`: create a production build.
- `npm run lint`: run ESLint.
- `npm run preview`: serve the production build locally.

### `frontend/vite.config.js` and `frontend/eslint.config.js`

`vite.config.js` enables the React plugin for Vite. `eslint.config.js` enables
the JavaScript recommended rules plus the React Hooks and React Refresh rules.

## Voice Examples

The files under `examples/` are independent utilities using Pocket TTS.
They use `torch.cuda.is_available()` to select `cuda` or `cpu`.

### `examples/recordvoice.py`

Starts a Tkinter recorder. `VoiceRecorder` stores microphone callback frames,
then writes `my_recorded_voice.wav` at 24,000 Hz as 16-bit PCM when recording
stops. The sounddevice callback receives input audio, frame count, timing
metadata, and status; only the input audio is retained.

Run it from `examples/`:

```powershell
cd .\examples
python .\recordvoice.py
```

### `examples/voice_clone.py`

Defines `CloneStudio`, a Tkinter UI that records a sample and accepts text.
It uses `TTSModel`, `sounddevice`, NumPy, and SciPy. The visible methods are:

- `__init__(root)`: receives a Tk root and initializes state and the UI.
- `build_ui()`: creates controls; returns `None`.
- `toggle_recording()`, `start_recording()`, `stop_recording()`,
    `capture_audio(...)`: control recording and write `my_recorded_voice.wav`.
- `start_clone()`: loads the recorded voice and generates the typed text into
    `clone_output.wav`.
- `play_output()`: plays the generated WAV file when available.

### `examples/run_clone.py`

Loads `TTSModel`, reads `my_recorded_voice.wav` as a voice prompt, generates a
fixed sentence, and writes `clone_output.wav`. It has no function arguments;
all input and output paths are hard-coded relative to the current directory.

### `examples/basictts.py`

Loads Pocket TTS, uses the built-in `alba` voice prompt, generates a fixed
sample sentence, and writes `output.wav`. It has no function arguments.

## Current Limitations

- Meeting notes and transcripts are local files, not request uploads.
- The API has no authentication or persistence.
- ChromaDB data is recreated for each analysis request.
- Ollama must be running locally and have the configured model available.
- The first request can be slow due to model downloads and model loading.
- The frontend backend URL is hard-coded to `127.0.0.1:8000`.
- The voice examples require microphone/audio-device access and are separate
    from the React UI.
